# P10 第三段計畫 — OpenDSM 1.2.7 重跑節能基準（事前登記）

> 2026-10-04 寫定，在任何 OpenDSM 模型結果產生之前。前兩段見 [`P10_PLAN.md`](P10_PLAN.md)、[`P10B_PLAN.md`](P10B_PLAN.md)。
> 本檔 commit 之後才寫執行程式；commit 時間就是登記時間。

## 為什麼做

P10 第二段用的 `eemeter` 4.1.1（2025-02）已是舊名。專案改名 **OpenDSM**，由 LF Energy 維護，PyPI `opendsm` 最新版 1.2.7（2026-02-11）；`eemeter` 套件停在 4.1.1 沒有再更新。
要回答兩個問題：

1. **換成現行套件，第二段的數字會不會變？**
2. **OpenDSM 的新小時模型 `HourlyModel`（不是 CalTRACK 2.0 小時法）給出的跨年差異，站在哪一邊？**第二段的官方模型 −19.1%、簡化版 −3.3%，差了 15.8 個百分點。

## 先讀過的實裝事實（opendsm 1.2.7，2026-10-04 讀已安裝的原始碼）

| 項目 | 實裝行為 | 對本設計的影響 |
|---|---|---|
| 安裝 | 在本專案的 Python 3.14 環境 **import 即失敗**；Python 3.13 也一樣。根因不是 Python 版本，是傳遞依賴：`multimethod` 2.1（2026-07-29 發布，晚於 opendsm 1.2.7）與 `scikit-fda` 0.10.1 衝突，報 metaclass conflict | 依第二段的停損規則不改套件原始碼。另建 `.venv-opendsm`（Python 3.13），釘 `multimethod==2.0.2`。共用 `.venv` 不動，`eemeter` 4.1.1 留著 |
| CalTRACK 小時模型 | `opendsm.eemeter.HourlyCaltrackModel`。把 `models/hourly_caltrack/` 九個檔去掉授權檔頭、註解與 import 後逐行比對 eemeter 4.1.1：**只有 `metrics.py` 多包一層除以零的警告抑制，其餘零差異** | 模型本體沒變，預期數字與第二段相同 |
| 充足性檢查 | `eemeter/common/sufficiency_criteria.py` 改動很大（正規化後 630 行差異） | 警告清單可能與第二段不同，照原樣列出 |
| 新小時模型 | `opendsm.eemeter.HourlyModel`：整年一個彈性網路迴歸，時間分群（temporal cluster）當類別特徵、溫度分箱與交互項；無 GHI 時用 `HourlyNonSolarSettings`（`train_features=["temperature"]`） | 本資料沒有日射量，用非太陽能設定 |
| 溫度單位 | 新模型固定分箱 `[10, 30, 50, 65, 75, 90, 105]`，**華氏** | 外氣溫照舊先換 °F |
| 基準長度 | 新模型的充足性：最短 `ceil(0.9×365)`＝329 天、最長 366 天 | 358 天的基準在新模型下應該不再被標記（第二段的 CalTRACK 檢查要求剛好 365 天） |
| 不合格機制 | 新模型有 `cvrmse_threshold=1.4`、`pnrmse_threshold=2.2`；資料或模型不合格時 `fit`／`predict` 會丟 `DisqualifiedModelError`，除非 `ignore_disqualification=True` | 先不帶 ignore 跑；被擋下就照實記錄原因，再帶 ignore 跑出數字並標明 |
| 隨機性 | `seed` 預設 `None`，每次用隨機種子（影響彈性網路與分群） | 主比較固定 `seed=42`，另跑 5 個種子報範圍 |
| 不確定度 | `uncertainty_alpha=0.1`（90%） | 與第二段同口徑 |

## 設計（寫死）

資料、報告期（2025-01-01～05-31）、兩段工況切法、負值設缺值、°F 換算，全部沿用第二段。`is_electricity_data=False`。

| 編號 | 方法 | 基準期 | 用途 |
|---|---|---|---|
| **N1** | OpenDSM `HourlyCaltrackModel` | 2024-01-01～12-31 | 與第二段 M1（eemeter 4.1.1，數字取自已 commit 的 `reports/p10b_monthly.csv`）逐月對帳 |
| **N2**（主比較） | OpenDSM `HourlyModel`，非太陽能設定，seed=42 | 同上 | 新模型的跨年未解釋差異 |
| M2 | 簡化版 `frozen_towt` | 同上 | 同環境重跑的對照組，應重現第二段的 −3.3% |
| N3 | `HourlyModel` | 2024-01-08～12-31 | 358 天基準在新充足性檢查下是否仍被標記 |
| N4 | `HourlyModel` | 2024-01-01～12-31，去掉 10/16–11/7 | 事件敏感度 |
| N5 | `HourlyModel`，seed 0–4 | 同 N2 | 種子造成的合計差異範圍 |

**輸出**
1. N1 對 M1 的逐月差（百分點）。
2. 充足性警告與不合格原因（N1、N2、N3），照原樣列。
3. 基準期樣本內每小時與每月 CV(RMSE)、NMBE（N1、N2、M2，同一個 `mv_metrics`）。
4. 報告期逐月與合計的「調整後基準 − 實際」，兩段工況分開（N1–N4、M2）。
5. N2 逐月差異是否超出模型自己的 90% 不確定度。
6. 守門：竄改報告期實際值，N2 的調整後基準不得改變；植入 15% 節能，回收值應等於不吸收時的應得值。

## 事前預期（寫下來，結果不符照實報告）

1. **N1 與 M1 逐月差都在 0.1 個百分點以內。**理由：模型程式碼逐行相同。若不符，差異來源只可能是資料前處理或充足性檢查改動，要追到是哪一個。
2. **N2 合計落在 −10% 以下，靠 M1（−19.1%）那一邊。**理由：新模型雖然整年只配一個迴歸，但時間分群會把冬季月份分成自己的群，冬季水準主要由 2024 冬季的基準資料決定，效果接近 CalTRACK 的月份分段。
   這是本輪最主要的可證偽預測：若 N2 落在 −10% 以上（靠簡化版那一邊），代表「分群等於分段」的推理有誤。
3. **N4 與 N2 合計差 < 2 個百分點。**理由同 2：1–5 月所屬的群不含 10/16–11/7。
4. **N3 不再出現基準天數的警告或不合格。**
5. **N5 五個種子的合計差異範圍 < 1 個百分點。**若超過，新模型在這份資料上的結果就要連同種子範圍一起報，不能只報單一數字。
6. N2 的基準期每月 CV(RMSE) 過 Guideline 14 的 15%。

## 判讀規則

沿用第二段，另加兩條：

- N1 對 M1 的對帳只回答「套件改名有沒有改變數字」，不產生新結論。
- N2 若與 N1 差超過 5 個百分點，報告寫成「**同一個官方套件裡的兩個小時模型給出不同答案**」，兩個都列，不挑一個當結論。差異仍叫未解釋差異，不是節能量。

## 停損

- `.venv-opendsm` 裡 fit 或 predict 失敗：記錄錯誤原文，不改 opendsm 原始碼；`DisqualifiedModelError` 依上表處理，其他錯誤只交本登記與失敗紀錄。
- 結果出來後想加的分析一律標「事後」，不改本檔的主比較。

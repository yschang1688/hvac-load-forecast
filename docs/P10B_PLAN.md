# P10 第二段計畫 — OpenEEmeter（CalTRACK 小時模型）對照簡化版基準（事前登記）

> 2026-10-02 寫定，在任何 eemeter 模型結果產生之前。第一段見 [`P10_PLAN.md`](P10_PLAN.md) 與 [`../reports/P10_REPORT.md`](../reports/P10_REPORT.md)。
> 本檔 commit 之後才寫執行程式；commit 時間就是登記時間。

## 為什麼做

P9、P10 的基準模型是自己寫的簡化版「時段 × 溫度」迴歸。概念取自 CalTRACK，但不是官方實作，而且沒有達到 Guideline 14 的校準準則（P10 每小時 CV 36.8%、每月 22.1%）。
要回答的問題只有一個：**換成官方實作，P10 的結論還站得住嗎？**特別是 P10 §三 的發現：「全年基準最準，是因為基準期混進了 10/16–11/7 的非例行事件」。

## 先讀過的實裝事實（eemeter 4.1.1，2026-10-02 讀原始碼）

文件可能比實裝新一個世代，所以以裝好的那一份為準。

| 項目 | 實裝行為 | 對本設計的影響 |
|---|---|---|
| 模型 | `eemeter.HourlyCaltrackModel`（`models/hourly_caltrack/`）：CalTRACK 2.0 小時模型。另一個 `eemeter.HourlyModel` 是 4.x 新模型，不是 CalTRACK，本輪不用 | 只跑 `HourlyCaltrackModel` |
| 分段 | 固定 `three_month_weighted`：每個月份一個模型，該月權重 1、前後月 0.5 | 1–5 月的模型只看 12–6 月的基準資料，**不會看到 10/16–11/7 事件** |
| 佔用 | 每段依「hour of week」估高低負載，門檻 0.65，迴歸用 `cdd_65`、`hdd_50` | 這兩個是**華氏**度日 |
| 溫度分箱 | 預設端點 `[30, 45, 55, 65, 75, 90]`，**華氏** | 外氣溫必須先從 °C 換成 °F，否則分箱全錯 |
| 充足性 | `caltrack_sufficiency_criteria`：資料跨度要**剛好 365 天**；有效日比例 ≥ 0.9；負值記為嚴重警告（CalTRACK 2.3.5，原意是太陽能逆送） | 只產生警告，不會擋下 fit |
| 假日 | 模型沒有假日變數 | 和簡化版不同，照實記錄 |
| 不確定度 | `predict` 回傳 ASHRAE 14 型的逐月不確定度，α＝0.1（90% 信賴） | 可用來判斷差異是否大於模型自己的不確定度 |
| `is_electricity_data` | True 時把 0 當缺值 | 冷量不是電，設 False |

## 資料（剖析結果，建模前）

- 目標沿用 P10：**WC000 自算冷量**（流量 × ΔT × 1.163），每小時平均 kW，等於該小時 kWh。
- 2024 年資料從 2024-01-01 01:00（當地）開始，第一週 167 小時全有值。P9、P10 從 01-08 起算是沿用 P8 的起點，並非資料缺失。
- **2024-01-01 起算，有效資料跨度 365 天**，符合 CalTRACK；從 01-08 起算只有 358 天，會被標成 `incorrect_number_of_total_days`。
- 2024 年有 11 天冷量覆蓋率 < 90%（有效日比例約 97%，過 0.9 門檻）。
- 自算冷量為負值：2024 年 3 小時、2025 年 4 小時（回水溫低於供水溫）。為 0 的有 5 小時。

## 設計（寫死）

**負值處理**：兩種方法吃同一份輸入。負值小時設為缺值（物理上不可能，且會觸發與本資料無關的太陽能警告）。這個處理讓簡化版的數字可能和 P10 主分析差一點點，所以簡化版也在新輸入上重跑。

| 編號 | 方法 | 基準期 | 報告期 | 用途 |
|---|---|---|---|---|
| **M1**（主比較） | eemeter `HourlyCaltrackModel` | 2024-01-01 ～ 12-31 | 2025-01-01 ～ 05-31 | 官方實作的跨年未解釋差異 |
| **M2**（主比較） | 簡化版 `frozen_towt`（P9 設定不變，含假日） | 2024-01-01 ～ 12-31 | 同上 | 同一窗、同一輸入的對照組 |
| M3（參照） | eemeter | 2024-01-08 ～ 12-31 | 同上 | 示範 358 天基準被充足性檢查標記；不進主結論 |
| M4（敏感度） | eemeter | 2024-01-01 ～ 12-31，去掉 10/16–11/7 | 同上 | 對照 P10 §三 的「去掉事件」 |

- 報告期照 P10 拆兩段：高供水溫工況（01-01 ～ 05-10）、回到 2024 工況（05-11 ～ 05-31）。
- 外氣溫：P10 同一來源，換算 °F＝°C × 9/5 + 32 後才進 eemeter；簡化版維持 °C。

**輸出**
1. eemeter 充足性警告清單（M1、M3），照原樣列出 `qualified_name`。
2. 基準期樣本內每小時與每月 CV(RMSE)、NMBE（M1、M2，同一個 `mv_metrics`，NMBE 正＝低估）。
3. 報告期逐月與合計的「調整後基準 − 實際」百分比（M1–M4），兩段工況分開。
4. M1 逐月差異是否超出 eemeter 自己的 90% 不確定度。
5. 守門：竄改報告期實際值，M1 的調整後基準不得改變；植入 15% 節能，M1 回收值應等於不吸收時的應得值。

## 事前預期（寫下來，結果不符照實報告）

1. **M1 的基準期每小時 CV(RMSE) 低於 M2。**理由：逐月分段加佔用分群，比單一全年迴歸更有彈性。
2. **M1 的報告期合計比 M2 更負，落在 −5% 以下，接近 P10 §三「去掉事件」的 −10%。**理由：1–5 月的分段模型只看 12–6 月的基準，10/16–11/7 事件進不來，等於自動做了 P10 §三 手動做的那一刀。
   這是本輪最主要的可證偽預測：若 M1 合計落在 −5% 以上（例如接近 −2.7%），代表上面的機制推理有誤，要回頭查分段權重。
3. **M4 與 M1 幾乎相同**（差 < 1 個百分點），理由同 2。
4. M1 的 2–3 月仍是最負的月份（實際比基準多），和 P10 主分析同向。

## 判讀規則

- 「兩種方法同向」＝逐月差異正負號在 5 個月中至少 4 個相同。
- 方法差＝M1 合計 − M2 合計，以百分點報告，不做顯著性檢定（一座機房、一個報告期）。
- 差異仍叫「未解釋差異」，不是節能量，也不是模型誤差（P10 §一.2 的運轉變更未解）。
- M1 若達到 Guideline 14 的 30%／15%，**只能說基準模型校準過關**，不能說節能量可信；報告期工況變更的問題不因模型而消失。

## 停損

- eemeter 在 Python 3.14 上 import 或 fit 失敗：記錄錯誤，**不改 eemeter 原始碼**；改用獨立 venv（較舊 Python）重試一次，再失敗就只交本登記與失敗紀錄。
- 結果出來後如果想加分析，一律標「事後」，不改本檔的主比較。

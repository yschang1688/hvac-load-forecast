# P10 第二段 — OpenEEmeter（CalTRACK 小時模型）對照簡化版基準

P9、P10 的基準是自己寫的簡化版「時段 × 溫度」迴歸。這一段換成官方實作 OpenEEmeter 4.1.1 的 `HourlyCaltrackModel`，用同一份資料、同一個報告期再算一次。
設計在任何 eemeter 結果出來之前寫進 [`docs/P10B_PLAN.md`](../docs/P10B_PLAN.md)（commit db2d128）。
> 後續：`eemeter` 已改名 OpenDSM。用 opendsm 1.2.7 重跑的結果見 [P10 第三段](P10C_REPORT.md)：本頁的 CalTRACK 數字完全重現，另多一個新小時模型的對照。

```bash
uv pip install --python .venv/bin/python eemeter   # 4.1.1；只新增套件，不動既有版本
.venv/bin/python src/run_p10b.py                   # 約 25 秒；前置資料同 P10
```

## 一句話

**官方模型的基準校準過了 Guideline 14，報告期的未解釋差異卻是 −19.1%，比簡化版的 −3.3% 多出 16 個百分點，五個月都超出它自己的 90% 不確定度。**
換一個基準模型，帳面上的「節能量」就差十幾個百分點。所以量測驗證計畫要在報告期開始前就寫死用哪個模型。

## 一、先讀實裝才知道的三件事

| 實裝行為 | 不讀原始碼會怎樣 |
|---|---|
| 溫度分箱端點 `[30, 45, 55, 65, 75, 90]`，佔用分群用 `cdd_65`、`hdd_50`，**全是華氏** | 直接餵攝氏，分箱與佔用全錯，而且不會報錯 |
| 充足性檢查要求資料跨度**剛好 365 天** | P9／P10 從 01-08 起算只有 358 天，會被標成 `incorrect_number_of_total_days`（M3 實測如此） |
| 固定 `three_month_weighted` 分段：每個月份一個模型，當月權重 1、前後月 0.5 | 1–5 月的模型只看得到 12–6 月的基準資料 |

另外：4.x 的 CalTRACK 類別在 `eemeter.eemeter` 子套件，頂層 `eemeter` 沒有匯出；頂層的 `HourlyModel` 是另一個新模型，不是 CalTRACK。

## 二、結果（主比較 M1 對 M2，同一基準窗 2024-01-01 ～ 12-31、同一輸入）

| | M1 eemeter | M2 簡化版 |
|---|---|---|
| 基準期每小時 CV(RMSE)／NMBE | **26.9%**／+0.2% | 36.9%／+0.0% |
| 基準期每月 CV(RMSE)／NMBE | **10.0%**／+0.2% | 21.8%／+0.0% |
| Guideline 14-2002（30%／15%） | 過 | 沒過 |
| 2025-01 | −13.5% | −7.2% |
| 2025-02 | −17.3% | −15.3% |
| 2025-03 | **−42.0%** | −13.6% |
| 2025-04 | −17.9% | +5.6% |
| 2025-05 | −11.4% | +6.5% |
| **合計** | **−19.1%** | **−3.3%** |
| 高供水溫工況 01-01 ～ 05-10 | −19.0% | −4.7% |
| 回到 2024 工況 05-11 ～ 05-31 | −20.0% | +3.6% |

差異＝調整後基準 − 實際，負值代表實際比基準多。同向月份 3/5（4、5 月相反），方法差 −15.8 個百分點。
M2 和 P10 主分析（−2.7%）差 0.6 個百分點，因為基準改從 01-01 起算、負值小時設為缺值。

**M1 逐月差異對 eemeter 自己的 90% 不確定度（ASHRAE 14 型）**：五個月全部超出。例如 3 月差 −78.3 MWh，不確定度 ±5.1 MWh。

**守門與植入**：竄改報告期實際值，M1 的調整後基準不變；植入 15% 節能，回收值等於不吸收時的應得值（被吃掉 0.00%）。P9 的紀律在官方模型上一樣成立。

**充足性警告**：M1 只有一個非嚴重警告 `extreme_values_detected`（129 小時超過中位數＋3 IQR，最大 3,617 kW，CalTRACK 2.3.6 要求人工複查）。M3（01-08 起）多一個嚴重警告 `incorrect_number_of_total_days`（358 天）。

## 三、對照事前預期

| 事前預期 | 結果 |
|---|---|
| 1. M1 基準期每小時 CV 低於 M2 | **相符**：26.9% 對 36.9% |
| 2. M1 合計落在 −5% 以下，接近 P10 §三「去掉事件」的 −10% | **方向相符，幅度不符**：−19.1%，比預期更負 |
| 3. M4（去掉 10/16–11/7 事件）與 M1 差 < 1 個百分點 | **相符**：逐月與合計完全相同 |
| 4. 2–3 月仍是最負的月份 | **相符**：3 月 −42.0%、2 月 −17.3%（4 月 −17.9% 與 2 月相近） |

**預期 2 錯在哪**：我推理到「1–5 月的分段看不到 10–11 月事件」為止（預期 3 證實了這點），卻沒想到下一步：
三個月加權分段本身就是一個**同季基準**。它拿 2024 年 12–6 月的水位來預測 2025 年 1–5 月，而 P10 §三 已經量過，用同季當基準的結果是 −20.2%。
M1 的 −19.1% 幾乎就是那個數字。所以 M1 不是「去掉事件的全年基準」，而是「同季基準」，這兩個在這份資料裡差 10 個百分點。

## 四、讀法

1. **校準過關不代表報告期可信。** M1 的月度 CV 10%，是 M2 的一半，報告期卻偏離得更多，五個月都超出它自己的不確定度。
   基準期擬合得越貼，對「隔年工況還是一樣」這個假設越敏感。這份資料的 2025 年冬春冷量本來就比 2024 年同期高（P10 §三：2 月 +34%、3 月 +43%）。
2. **模型選擇就能讓帳面節能差 16 個百分點。** M1 和 M2 都是合理的 CalTRACK 系做法，差別只在「季節性怎麼處理」：一個全年模型，一個逐月模型。
   在分享節能合約裡，這 16 個百分點就是錢。所以模型、基準窗、非例行事件的處理要在報告期之前寫進量測驗證計畫，事後不能挑。
3. **P10 §三 的結論更穩了。** 官方模型自動排除了 10–11 月事件（M4＝M1），而且結果遠離 −2.7%。簡化版全年基準的「最準」確實來自基準期被事件污染。
4. **未解釋差異仍然未解釋。** 回到 2024 工況的 05-11 ～ 05-31，M1 仍是 −20.0%，所以差異不只來自供水溫偏高那段工況。這份資料沒有電表、沒有維修紀錄，分不出是負載真的變了、量測漂移，還是別的原因。

## 誠實邊界

- 一座機房、一個報告期，描述性結果，沒有顯著性檢定。
- CalTRACK 是為建築**電表**設計的；這裡套在冰水機房的**冷量**上，佔用分群與度日假設不一定合適。沒有假日變數。
- 目標只有 WC000 自算冷量一個來源（P10 §一）。
- eemeter 不確定度的公式取自實裝程式碼（ASHRAE 14 型，α＝0.1），沒有對照原文核算。
- eemeter 沒有加進 `requirements.txt` 與 CI（numba 等相依很重）；守門檢查在執行腳本裡跑，沒有獨立測試。
- §三 的「預期 2 錯在哪」是看過結果後的解釋，對照 P10 §三 已有的數字，但沒有另外驗證。

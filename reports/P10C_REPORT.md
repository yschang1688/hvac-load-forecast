# P10 第三段 — OpenDSM 1.2.7 重跑節能基準

第二段用的 `eemeter` 4.1.1 已是舊名。專案改名 **OpenDSM**（LF Energy），PyPI `opendsm` 最新版 1.2.7（2026-02-11），`eemeter` 套件停在 4.1.1（2025-02）。
這一段用現行套件把節能基準重跑一次。設計在任何 OpenDSM 結果出來之前寫進 [`docs/P10C_PLAN.md`](../docs/P10C_PLAN.md)（commit 76804d2）。

```bash
uv venv .venv-opendsm --python 3.13          # 共用 .venv（Python 3.14）裝不起來，原因見 §一
uv pip install --python .venv-opendsm/bin/python -r requirements-opendsm.txt
.venv-opendsm/bin/python src/run_p10c.py     # 約 30 秒；前置資料同 P10
```

## 一句話

**套件改名沒有改變 CalTRACK 的數字（−19.1%，逐月差 0.000 個百分點）。但 OpenDSM 裡的新小時模型給 −12.1%，同一個官方套件的兩個小時模型差 7 個百分點。**
加上簡化版的 −3.3%，同一份資料現在有三個「合理」的答案：−19.1%、−12.1%、−3.3%。

## 一、先讀實裝才知道的事

| 實裝行為 | 不讀原始碼會怎樣 |
|---|---|
| opendsm 1.2.7 在 Python 3.14 **import 就失敗**，Python 3.13 也一樣。根因是 `multimethod` 2.1（2026-07-29，比 opendsm 1.2.7 晚五個月）與 `scikit-fda` 0.10.1 衝突，報 metaclass conflict | 會以為是 Python 版本太新而一路降版。實際釘 `multimethod==2.0.2` 就好 |
| `HourlyCaltrackModel` 的九個原始檔，去掉授權檔頭、註解與 import 後與 eemeter 4.1.1 逐行比對：只有 `metrics.py` 多一層除以零的警告抑制 | 會期待「新版官方實作」給出不同的 CalTRACK 結果 |
| OpenDSM 主推的是新的 `HourlyModel`：整年一個彈性網路、時間分群、溫度分箱。**它不是 CalTRACK 2.0 小時法** | 文件與外部摘要常把兩者都叫「CalTRACK 小時模型」 |
| 新模型的溫度分箱 `[10, 30, 50, 65, 75, 90, 105]` 仍是**華氏** | 直接餵攝氏不會報錯 |
| 新模型的基準長度門檻是 329–366 天；月覆蓋率低於 90% 會讓資料**不合格**，`fit` 直接丟例外 | 第二段的 CalTRACK 檢查要求剛好 365 天；兩個模型的充足性規則不同 |
| 新模型會內插缺的外氣溫再預測；CalTRACK 模型遇到缺溫度就不預測 | 兩個模型涵蓋的小時數不同（3,538 對 3,463），合計不是同一批小時 |
| 不確定度欄位從 `predicted_uncertainty` 改名 `predicted_unc` | 沿用第二段的程式會靜默跳過 |

## 二、結果（基準 2024-01-01～12-31，報告 2025-01-01～05-31，同一輸入）

| | N1 OpenDSM CalTRACK | N2 OpenDSM HourlyModel | M2 簡化版 |
|---|---|---|---|
| 基準期每小時 CV(RMSE)／NMBE | 26.9%／+0.2% | 29.2%／−0.1% | 36.9%／+0.0% |
| 基準期每月 CV(RMSE)／NMBE | 10.0%／+0.2% | **9.7%**／−0.1% | 21.8%／+0.0% |
| 1 月 | −13.5% | −16.3% | −7.2% |
| 2 月 | −17.3% | −24.9% | −15.3% |
| 3 月 | −42.0% | −26.7% | −13.6% |
| 4 月 | −17.9% | −14.0% | +5.6% |
| 5 月 | −11.4% | **+9.9%** | +6.5% |
| **合計** | **−19.1%** | **−12.1%** | **−3.3%** |
| 高供水溫工況 01-01～05-10 | −19.0% | −15.6% | −4.7% |
| 回到 2024 工況 05-11～05-31 | −20.0% | +4.6% | +3.6% |

數字是「調整後基準 − 實際」占基準的比例，負值代表實際比基準多。N1、N2 都過 Guideline 14 的每小時 30%、每月 15%。

- **N1 對第二段 M1**：五個月與合計的差都是 0.000 個百分點。套件改名不影響 CalTRACK 結果。
- **N2 對 N1**：合計差 7.0 個百分點，超過事前訂的 5 個百分點。依判讀規則，兩個都列，不挑一個當結論。
- **差最多的是 3 月與 5 月**。3 月 CalTRACK −42.0%、新模型 −26.7%；5 月兩者連正負號都相反。回到 2024 工況的那三週，CalTRACK 說 −20.0%，新模型說 +4.6%。
- **同小時集合（事後）**：只算兩個模型都有預測的 3,463 小時，N2 是 −12.6%，結論不變。

**敏感度**

| | 合計 | 說明 |
|---|---|---|
| N3 基準從 01-08 起（358 天） | −10.5% | 沒有天數警告；但 1 月從 −16.3% 變 −6.0%，少一週基準就差 10 個百分點 |
| N4 去掉 10/16–11/7 事件 | −14.9% | **資料不合格**（10 月覆蓋率 48%），是帶 `ignore_disqualification` 跑的；5 月從 +9.9% 變 +1.3% |
| N5 種子 0–4 | 全部 −12.14% | 種子對結果沒有影響 |

**守門與植入（N2）**：竄改報告期能耗，基準不變；植入 15% 節能，回收 +4.7%，等於不吸收時的應得值，被吃掉 0.00%。

## 三、事前預期對照

| # | 預期 | 結果 |
|---|---|---|
| 1 | N1 與 M1 逐月差 < 0.1 個百分點 | ✅ 0.000 |
| 2 | N2 合計在 −10% 以下，靠 CalTRACK 那邊 | ✅ −12.1%，但理由只對一半（見下） |
| 3 | N4 與 N2 差 < 2 個百分點 | ❌ 差 2.8 個百分點 |
| 4 | N3 不再有基準天數警告 | ✅ |
| 5 | 種子範圍 < 1 個百分點 | ✅ 0.00 |
| 6 | N2 每月 CV 過 15% | ✅ 9.7% |

**預期 3 錯在哪**：我假設「時間分群等於月份分段」，所以 1–5 月碰不到 10–11 月的事件。實際上去掉事件後，5 月從 +9.9% 掉到 +1.3%，其他月份幾乎不動。
最可能的解釋是 5 月與 10 月被分進同一個過渡季的群，事件期間偏高的冷量把 5 月的基準抬高了。這是看過結果後的解釋，沒有另外把分群結果印出來驗證。
所以預期 2 雖然數字對了，「分群等於分段」這個推理只在冬季月份成立。

## 四、讀法

1. **「用官方實作」不是一個答案，是兩個。** OpenDSM 同時提供 CalTRACK 2.0 小時法與新的小時模型，兩者基準期都校準過關（月度 CV 10.0% 與 9.7%），報告期卻差 7 個百分點，5 月正負號相反。
   量測驗證計畫只寫「依 CalTRACK／OpenDSM」不夠，要寫到模型類別與版本。
2. **第二段的讀法更強了，不是更弱。** 第二段說「模型選擇就能讓帳面節能差 16 個百分點」，那時是官方對自製。現在兩個都是官方模型，仍差 7 個百分點。
3. **新模型對基準期內容更敏感。** CalTRACK 的月份分段讓 1–5 月完全碰不到 10–11 月事件（第二段 M4＝M1）；新模型會（N4 差 2.8 個百分點）。少一週基準資料，1 月就差 10 個百分點（N3）。
4. **新模型會擋下不合格的資料，這是好事。** 去掉事件後 10 月只剩 48% 覆蓋率，`fit` 直接拒絕。第二段的 CalTRACK 模型對同一份資料沒有任何反應。
   「把非例行事件挖掉」這個常見做法，在新模型下會讓基準本身不合格，得另外處理。
5. **未解釋差異仍然未解釋。** 三個模型在 1–3 月都是負的（實際比基準多），這個方向是穩的；幅度與 4–5 月的方向則取決於模型。

## 誠實邊界

- 一座機房、一個報告期，描述性結果，沒有顯著性檢定。
- 兩個模型都是為建築**電表**設計的，這裡套在冰水機房的**冷量**上。本資料沒有日射量，新模型用非太陽能設定。
- N2 的逐月不確定度（每月約 ±1.6 MWh）是把逐點不確定度平方和開根號，等於假設各小時獨立，**一定低估**。OpenDSM 另有含自相關校正的 ASHRAE 14 合計公式，本輪沒有取用。所以「五個月都超出不確定度」這句話對 N2 不能照第二段的口徑引用。
- N4 是在不合格資料上強制跑出來的，只當敏感度參考。
- §三「預期 3 錯在哪」是事後解釋，沒有驗證分群結果。§二的同小時集合也是事後加的。
- OpenDSM 沒有加進 `requirements.txt` 與 CI：它需要獨立的 Python 3.13 環境與一個釘版的傳遞依賴。守門檢查在執行腳本裡跑，沒有獨立測試。
- 釘 `multimethod==2.0.2` 是繞過上游依賴衝突的作法，沒有回報給 OpenDSM 或 scikit-fda。

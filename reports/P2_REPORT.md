# P2 — 防洩漏特徵管線與切分

## 時序洩漏有兩種，第二種不會被 shift/rolling 的檢查抓到

**第一種：用未來的負荷算過去的特徵。**
靠 `shift(1)` 起算的滾動統計可防，並以**行為檢測**釘死——把序列尾端整段竄改後重算，
`build_design` 的每一欄在前段都必須逐格不變。這抓的是「實際上有沒有用到未來」，
不是「程式碼裡有沒有寫 shift」。

**第二種：用「實際的未來天氣」當特徵。**
day-ahead 預測在生產環境只拿得到氣象**預報**，離線卻常直接餵實測值——
等於假設預報零誤差。程式上完全合法，任何靜態檢查都抓不到，但上線就會掉下來。

本專案把它做成明碼開關，而不是預設值：

| `weather_mode` | 未來天氣欄位 | 意義 |
|---|---|---|
| `perfect_forecast` | 48 欄（`fut_*_h1…h24`） | 完美預報的**上界** |
| `lagged_only` | 0 欄 | 無預報可用時的**下界** |

**兩種都跑，差距就是氣象預報對這個模型值多少。** 只報其中一個都是片面的——
P3 會把這個差距量出來。

### 設計上的一個修正（過程記錄）

初版把未來天氣寫在 `build_design` 裡、用 `weather_mode` 切換要不要 shift。
實際檢查才發現：兩種模式的特徵列都索引在 t、用的都是 t 當下的天氣，
差別只有 lag 1 —— **`perfect_forecast` 這個名字承諾了它沒有做的事**。
已改為逐 horizon 的獨立區塊 `future_weather_block`（欄位一律 `fut_` 前綴自我標示），
於是 `build_design` 的紅線變成絕對的：`detect_lookahead` 回傳非空即為 bug，
沒有「這個欄位可以例外」的情況。

## 切分：rolling-origin，禁用隨機切分

- 訓練段永遠在驗證段之前，兩者之間留 **gap = horizon（24h）**，
  否則訓練集尾端的標的（t+1…t+24）會伸進驗證段。
- 6 個 fold，各驗證 30 天：2017-01 → 2017-06。
- **2017-07-01 之後全程封存**，模型選擇期間不得觸碰；`rolling_origin_splits`
  內建守衛，任何 fold 伸進封存期就直接 assert 失敗。

隨機切分在時序上的後果與 surface-defect 的分組洩漏同構，只是換一個維度：
同一天的鄰近小時同時落在訓練與測試，量到的是內插不是預測。

## 特徵與因果假設（JD 原文要求「被質疑時答得出來」）

| 特徵 | 因果假設 |
|---|---|
| `load_lag_1/2/3` | 建築熱慣性——前幾小時的負荷是當下最強的預測因子 |
| `load_lag_24/48/168` | 日內、隔日與週節律（週間／週末使用型態差異） |
| `load_roll_mean_24` | 近一日基準水準，吸收季節與營運狀態的緩慢漂移 |
| `load_roll_std_24` | 近一日波動度，區分穩定運轉與啟停頻繁的時段 |
| `airTemperature`、`dewTemperature` | 乾球溫度與露點決定顯熱與潛熱負荷，是冷卻負荷的物理驅動量 |
| `cloudCoverage` | 影響日射得熱 |
| `windSpeed` | 影響外殼熱傳與滲透 |
| 日曆（sin/cos、dow、is_weekend） | 佔用率的週期性代理變數 |

## 建模樣本

12 棟建築、跨 **7 個 site**（分層抽樣：每個 site 取品質最好的 2 棟，規則寫在設定檔）。
選取條件為 P1 判定非 Reject 且覆蓋率 ≥ 0.95，**在看到任何模型結果之前決定**。

## 守門測試（本階段 9 則，全檔 23 則全綠）

- 兩種 mode 下 `build_design` 皆不得偷看未來（行為檢測）
- **洩漏探針**：植入偷看未來 24h 的特徵，偵測器必須點名它——
  沒有這條，「偵測器沒抓到東西」可能只是偵測器壞了
- 未來天氣必須 opt-in 且以 `fut_` 前綴自我標示，並實際取到 t+h 的值
- 滾動統計必須自 `shift(1)` 起算（與手算逐格比對）
- 建構階段不得 dropna——樣本存在與否若取決於未來，切分就已被污染
- **封存段守衛**（含反向探針：把封存起點前推，切分函式必須翻臉）
- 訓練／驗證間隔必須 ≥ horizon

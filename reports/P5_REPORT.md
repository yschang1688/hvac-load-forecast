# P5 — 服務層、API contract 與排程

跑在**真的 PostgreSQL 17**（`docker compose up -d`，非 SQLite）——
UPSERT 用的是 PostgreSQL 的 `ON CONFLICT`，換引擎就測不到真正要測的東西。

## 為什麼需要這一層

從「一案場一客製」走向平台時，**最先崩的不是模型，是欄位**。
大金叫 `chwLoadKw`、開利叫 `CHW_LOAD_RT`，單位一個 kW 一個冷凍噸、溫度一個 °C 一個 °F、
時戳鍵名也不同。若讓方言直接流進模型，每接一個新案場就要改一次模型端程式碼——
那不是平台，只是把客製化搬到另一個檔案。

## 實跑證據

| 案場 | 廠牌方言 | 原始欄位 | canonical 結果 |
|---|---|---|---|
| DAIKIN_SITE | `vendor_a` | `chwLoadKw=100.0`（kW／°C） | **100.00 kW** |
| CARRIER_SITE | `vendor_b` | `CHW_LOAD_RT=28.4`（RT／°F） | **99.88 kW** |

兩套完全不同的方言，進系統後落在同一個尺度上（差 0.12 kW ＝ 換算捨入）。
**新增廠牌只加一筆 `VendorDialect`，不改 ingestion 程式。**

## 閘口：擋下並留紀錄，不是塞 None 往下傳

四類違規在閘口就被擋住，並回**結構化錯誤**（哪個欄位、什麼值、違反哪條規則）：

1. **負值** — 冰水側熱負荷無負值的物理意義（與 P1 的 R001 同一條規則）
2. **溫度超出地表可能範圍** — 多為單位或位元組序錯誤
3. **露點高於乾球溫度** — 物理不等式，單欄位驗證抓不到
4. **超過銘牌額定 1.5 倍** — 計量器溢位／單位錯誤

被擋下的資料**留下 `quality_events` 事件列**，不是悄悄丟棄——否則事後無從得知漏了什麼。

### 一個實跑才發現的缺口

首次端到端跑時，`chwLoadKw=1e9` **沒有被擋下**：契約層只驗了負值與溫度合理性，
沒有上限。而 P1 的 R002 上限是從**整段分布**估的，逐筆進來時沒有分布可用。

修法不是「用資料自身估一個上限」——P1 已證明零膨脹下那樣做會讓每個非零讀數都變違規。
正解是**上限必須來自設備銘牌**（`sites.capacity_kw`），而**沒有銘牌就不判**。
這條在 P1 報告的誠實邊界裡預言過，實跑時果然撞上。

## 資料模型（SQLAlchemy ORM，四張表）

| 表 | 回答的問題 |
|---|---|
| `sites` | 這個案場是誰、用哪套方言、銘牌額定多少 |
| `predictions` | 模型當時說了什麼（`issued_at` 與 `target_ts` 分開記） |
| `quality_events` | 閘門攔下了什麼、做了什麼處置 |
| `model_versions` | 哪個版本、用哪段資料訓的、**驗收指標多少**、為何重訓 |

兩個設計決定：

- **`issued_at` 與 `target_ts` 必須分開記**。只記其一就無法回答「這筆預測是提前幾小時做的」，
  也就無法歸因線上失準（P2 的教訓：特徵時戳與推論時戳分開記，才抓得到默默用舊資料的特徵）。
- **`(site_id, target_ts, horizon, model_version_id)` 唯一鍵＋UPSERT**。
  排程器會重試，重試不能產生重複列。實跑驗證：同一批預測寫兩次，總列數維持 48。

## 排程：兩個不綁排程器的純函式

`daily_predict`（每日預測，UPSERT 冪等）與 `weekly_retrain_check`（每週漂移檢查）
寫成不依賴 Airflow／APScheduler 的函式，排程器只負責觸發。
換排程器不用改業務邏輯，也讓它們能被單元測試直接呼叫
（邏輯寫在 operator 裡就測不到）。

**重訓觸發除了 PSI 門檻還有冷卻期**：沒有冷卻期，一段持續漂移會讓系統每週都重訓，
而每次重訓都要重新驗收，運維成本與模型抖動都會失控。實跑：
PSI=0.42（超過 alert 門檻 0.25）在冷卻期內回 `retrain=False`，冷卻期外才回 `True`。

### 守門測試抓到的缺陷

`ModelVersion.trained_at` 的 ORM 預設是 `utcnow()`（**牆鐘時間**）。
在部署回放或歷史模擬中，模擬時點是 2017、牆鐘是 2026，
「距上次重訓多久」算成負數 → 冷卻期永遠成立 → **重訓永遠不觸發，且完全不報錯**。
測試訊息是「在冷卻期內（還有 3489 天）」。已改為可注入並加守衛測試。

## 儀表板

`GET /sites/{site_key}/dashboard` 把**業務數字與品質狀態放同一頁**：
收進幾筆、閘口擋下幾筆（含百分比）、最近預測 vs 實際、模型版本與其驗收指標。
沿用 credit-risk 儀表板的原則——不把稽核結果藏在附錄。
輸出樣本：`reports/p5_dashboard.html`。

## 測試

全專案 **42 則**，其中本階段 12 則跑在真實 PostgreSQL 上（資料庫未啟動時整檔 skip
並如實標註）。涵蓋：兩方言歸一同尺度、違規回 422 帶理由、攔截留事件、
UPSERT 冪等（服務層與排程層各一）、無啟用模型回 409、冷卻期、
註冊新版本必停用舊版本、銘牌上限、無銘牌不猜、儀表板同頁。

## 誠實邊界

- **這是可運行原型，不是生產部署**：單節點容器、無認證授權、無 rate limiting、
  無連線池調校、無備份還原、無監控告警。**不得寫「生產環境 API 服務」。**
- 預測值由 `demo_p5.py` 以合成序列寫入，用來驗證資料流與冪等；
  **端到端「模型推論 → 落庫 → 儀表板」的串接尚未接上 P3 的實際模型**。
- `alembic` migration 未使用（以 `create_all` 建表）；多案場並行寫入的鎖競爭未測試。
